01 — What it is

Think of it as a small factory, not a single tool.

A car rolls down an assembly line and a different station adds the engine, the doors, the paint. This pipeline works the same way: a Baramundi deployment job goes in one end, and by the time it comes out the other, it has documentation, test cases, working automation code, a code review, and a verified test run — each produced by a different specialist "worker," handed off in sequence, with a person approving the one step that matters most before anything goes live.

1

Baramundi Documentation Agent

Baramundi's deployment scripts are dense, procedural files — not something a tester or reviewer wants to read directly. This agent distills them into a clean document: what the software is, what has to be true before it installs, the rules that define success, and which test cases map to it.

2

Requirement-to-Test Agent

Takes that documentation and writes concrete, structured test cases — the kind a human tester or Aqua Test Center can act on directly, not vague prose.

3

Script Adaptation Agent

When a requirement changes, this agent updates the actual automation script to match — and raises a real pull request for it, exactly like an engineer would, so the change is visible and reviewable, not silently applied.

4

Automation Review Agent

Reviews that pull request the way a second engineer would — quality, security, whether it actually traces back to the requirement — and posts a real GitHub review: approve or request changes.

5

Execution & Self-Healing Agent

Runs the approved script and captures evidence. If a test fails because the application's UI changed (a button's ID renamed, say), it asks the AI for a fix, re-runs the test to verify the fix actually works, and only then opens its own follow-up pull request. It never silently patches anything, and it never fakes a pass.

04 — Self-healing, walked through

What happens when the application's UI changes underneath a test.

This is the pipeline's standout capability — demonstrated live, not described in theory.

STEP 1
Test fails
A button's ID changed in the app. The test times out waiting for the old selector.
STEP 2
AI suggests a fix
Agent 5 shows the AI the broken selector and the page's current HTML, asks for a replacement.
STEP 3
Fix is verified
The script is patched on a new branch and the test is re-run for real — not assumed fixed.
STEP 4
Only then, a PR
If (and only if) the re-run passes, the fix is pushed and a follow-up pull request opens for review.
05 — Safety, quality, and operations

Built to be trusted, not just to work once.

  • Nothing merges without a human. Every code change from Agent 3 or Agent 5 goes through a real pull request and an approval gate before it touches the automation that actually runs.
  • Security-reviewed. A dedicated review found and fixed two real issues — a path-traversal gap in a folder safety check, and a case where an AI-suggested fix could have been crafted to inject code. Both are closed and covered by tests that prove the original attack no longer works.
  • Full audit trail. Every action every agent takes is logged and browsable — plus a report that traces each requirement to its pull request to its current pass/fail result, and a real test-reporting dashboard (Allure).
  • Runs itself. A file-watch inbox and scheduled regression checks mean the pipeline can trigger on a new or changed requirement without anyone running a command by hand.
  • Works with whichever AI provider is approved. Anthropic, OpenAI, and Azure OpenAI are all wired in and tested — plus a no-key demo mode for showing the pipeline without any billing at all.
  • Deployment-ready. Dependency versions are pinned, configuration loading is fixed and verified, and there's a written runbook plus a one-command health check for standing this up on a new machine.
