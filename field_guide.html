Orientation

What it is

Think of it as a small factory, not a single tool. A Baramundi deployment job goes in one end; by the time it comes out the other, it has documentation, structured test cases, working automation code, a code review, and a verified test run — each produced by a different agent, handed off in sequence, with a human approving the one step that actually matters before anything merges.

Every agent has a dry-run mode that does everything except call the AI or touch git/GitHub — the whole pipeline can be demoed with zero API cost and zero risk of a stray commit. Every agent also supports four AI backends (anthropic_api, openai_api, azure_openai, claude_cli) via one LLM_BACKEND setting, so it isn't locked to one provider.

Orientation

The 5 agents

01

Baramundi Documentation Agent

agent1_baramundi_doc/

Distills a real, procedural .bds deployment script (dozens of nested actions, embedded PowerShell) plus its XML/job config into a clean, plain-English knowledge document — the single source of truth every downstream agent reads from.

Takes in
.bds script, XML config, job config
Produces
README / requirements.md / testspec.md
python run_agent1.py --bds ... --xml-config ... --job-config ... --split --dry-run
02

Requirement-to-Test Agent

agent2_requirement_to_test/

Turns requirements.md into structured, concrete test cases as JSON first, then deterministically writes the Aqua Import CSV in code — never asking the model to produce CSV directly, which avoids a whole class of quoting/escaping bugs.

Takes in
requirements.md (from Agent 1)
Produces
aqua_import.csv + .json
python run_agent2.py --requirements ... --output-dir output --dry-run
03

Script Adaptation Agent

agent3_script_adaptation/

When a requirement changes, updates the real automation script to match and opens a real GitHub pull request — the model returns the full updated file (not a diff), which is simpler and more reliable to apply deterministically. If the requirement's already satisfied, it correctly does nothing rather than committing an empty change.

Takes in
a requirement .md + the current script
Produces
a branch + commit + real PR
python run_agent3.py --requirement ... --script ... --dry-run
04

Automation Review Agent

agent4_review/

Reviews the PR's diff for quality, security, and traceability, then posts a native GitHub review — approve or request changes — not just a comment. Runs under a second GitHub identity, since GitHub won't let an account review its own PR.

Takes in
a PR number
Produces
a real gh pr review (approve/request-changes)
python run_agent4.py --pr-number N --dry-run
05

Execution & Self-Healing Agent

agent5_execution_selfheal/

Runs the approved script, captures evidence, and — if a test fails because a UI selector no longer exists — asks the AI for a replacement, re-runs the test to verify the fix actually works, and only then pushes and opens a follow-up PR. Also generates a real Allure test-results report and refreshes the requirement traceability report after every run.

Takes in
a script + target page
Produces
test result, evidence, Allure report, (maybe) a self-heal PR
python run_agent5.py --script ... --target-page ...
Orientation

The approval gate

Between Agent 4's review and Agent 5's execution sits the one non-negotiable checkpoint: a human decides whether to merge. Nothing Agent 3 or Agent 5 writes ever reaches the automation that actually runs without that merge happening first — self-heal's own follow-up PRs go through the exact same gate, they don't get a shortcut just because an AI proposed them.

Running It

Running the full pipeline

orchestrator/run_pipeline.py runs all 5 agents in sequence, each as its own subprocess (matching how they'd be wired into a real CI/CD pipeline later).

python run_pipeline.py --dry-runfull mechanical pass, no AI/git side effects
python run_pipeline.py --job 7zip --target-page v2real run, second job, exercises self-heal

It can also trigger itself: orchestrator/auto_trigger.py watches an inbox folder for new jobs/requirements and runs scheduled regression cycles, so nothing has to be run by hand.

Running It

Job registry

Which demo job to run — Adobe Acrobat Reader DC or 7-Zip 24.09 — is data, not hardcoded logic. orchestrator/jobs.json is the single source of truth for each job's .bds/config inputs, which script Agent 3 adapts and Agent 5 runs, and its v1/v2 target pages. Both the orchestrator's --job flag and the dashboard's Job picker read from this same file.

Proving the pipeline works against two structurally different jobs (not just the original Adobe job) is what confirms it generalizes instead of being quietly hardcoded to one app.

Running It

The dashboard

A live, stdlib-only web server (dashboard/server.py) with no build step — serves the live event feed, run controls, the Allure report, and the traceability report all from one process.

Live view

Real-time pipeline stations (one per agent) plus a scrolling event feed, sourced from a durable SQLite audit trail so nothing is lost on refresh.

History tab

Every past run, browsable by run — pass/fail at a glance, full event detail on click.

Run controls

Pick a Job, a Target page, and an AI Backend, then Dry Run or Real Run - real run requires an explicit confirmation naming exactly what's about to happen.

Approval panel

Appears automatically when a run is waiting on a merge decision - Approve & Merge or Reject, right from the browser.

Light and dark themes are both fully supported, with a persistent toggle in the header.

Under The Hood

Observability & reporting

Durable audit trail

Every action every agent takes is written to dashboard/events.db (SQLite), grouped by a shared run ID so a full pipeline run - across all 5 agents and the orchestrator - shows up as one coherent story in History, not five disconnected logs.

Real Allure test reporting

Agent 5 writes real Allure results and regenerates a real Allure HTML report after every run - not a hand-built imitation. Results accumulate across both job suites (rather than resetting per run) so the report reflects the combined picture, and Allure's own retry grouping keeps repeated runs of the same test from inflating the count.

Requirement traceability report

Ties three things together that used to live in separate places: which requirement drove a given test, the GitHub PR that implemented it (live status, not a snapshot), and its current pass/fail result - plus a trend of the last 10 runs per test, so a currently-passing-but-flaky test doesn't look identical to a rock-solid one. Currently: 10/10 passing 4/10 with a dedicated PR 4 flagged flaky. It's honest about the other 6 - they were mirrored into the second job's suite during a refactor rather than driven through Agent 3 individually, and the report says so rather than overclaiming.

Under The Hood

Reliability & AI providers

Retries with backoff

Every agent's AI call now retries with exponential backoff (1s, 2s, 4s) on genuinely transient failures - rate limits, connection drops, timeouts, momentary server errors. Auth errors and bad requests are never retried, since no amount of waiting fixes a bad key or a malformed request.

Four real AI backends

Anthropic, OpenAI, and Azure OpenAI are all wired in and unit-tested; claude_cli shells out to this machine's own logged-in Claude CLI for zero-cost local demoing. Whichever the client ultimately approves, the pipeline is already built for it.

Auto-triggering

A file-watch inbox (new jobs or requirements dropped in) plus scheduled regression cycles mean the pipeline can run itself instead of needing a manual CLI invocation every time.

Under The Hood

Operations & deployment

  • Persistent dashboard service - runs under systemd --user with auto-restart, survives logout via lingering, not just a plain process that dies with the terminal.
  • Preflight health check - scripts/preflight_check.py verifies binaries, gh auth, each agent's .env, and the automation target's venv in one command; the dashboard's own /health endpoint covers a running instance.
  • Pinned dependencies - every requirements.txt uses exact versions verified to install and import cleanly, not loose ranges that could silently drift.
  • .env actually loads now - found during a deployment readiness pass that no agent ever actually loaded its .env file (python-dotenv wasn't wired in); fixed across all 5.
  • RUNBOOK.md - fresh-machine setup, common failure modes, and where every log/report actually lives.
Under The Hood

Security

A dedicated review of the pipeline's attack surface found and fixed two real issues, both verified with actual proof-of-concept exploits, not just reasoning:

Path-traversal bypass in the folder allow-list

Agent 5's "only run scripts under tests/" check was a plain string prefix test - tests/../../../etc/passwd passed it. Fixed to resolve the real path and verify containment.

AI-output code injection in self-heal

The AI's suggested selector was spliced into the test file's source with no validation - a crafted string could break out of its quoted literal and inject a Python statement, which would then execute immediately as part of self-heal's own verification step, before any human review. Fixed with a strict allowlist gate before anything is written to disk.

Everything else came back clean: no shell=True or string-built shell/SQL commands anywhere, secrets properly gitignored, nothing sensitive leaking into the audit trail.

Under The Hood

Testing the pipeline itself

Beyond the target application's own test suite (10 Playwright test cases across both jobs), the pipeline's own code has 174 unit tests across every module - parsing, report generation, safety checks, git-command building, retry logic, the job registry's shape - independent of any AI call, so a regression gets caught immediately rather than surfacing as a confusing failure three steps downstream.
